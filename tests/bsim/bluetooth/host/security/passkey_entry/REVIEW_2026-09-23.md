# RFC 9382 N 分支审查与性能记录（2026-09-23）

## 范围与可重复证据

- 原生 PE：`baseline/zephyr-pe @ 256e764458c`；直接替换实验：`spake/direct-replacement`；固定 N 实验：`spake/transformed-basis @ 402c1684135` 加本次 review 改动。直接替换实验中的 `N=G` 已知有恶意对端选点离线验证路径，不能成为最终主线。
- `tools/rfc9382_basis.py --check` 验证固件的 64 字节 N 与 [RFC 9382 §6](https://www.rfc-editor.org/rfc/rfc9382.html#section-6) 的压缩点一致。`tools/reference_vectors.py` 的输出与 C KAT 向量逐字节一致。
- `tools/chosen_point_regression.py` 对一个固定曲线样例复核旧攻击等式：`N=G` 时识别测试口令，RFC N 时同一等式不匹配测试候选。它只检查已知等式，不能证明不存在其他离线攻击。
- Windows 入口 `scripts/windows/simulate.ps1` 调用 WSL BabbleSim，固定 N 版本的 8 个场景在修改前、增加时延记录后、去掉重复 N 校验后各通过 1/1。原始报告保存在工作区 `simulation-results/review-baseline-20260923/`、`review-measured-20260923/`、`review-optimized-20260923/`。
- 原生 PE 基线使用同一 `nrf52_bsim/native` 平台、同一 `123456` 口令和相同计时边界运行 1/1；只在隔离工作树的测试程序中添加计时打印，补丁保存在 `simulation-results/review-pe-baseline-20260923/pe-baseline-instrumentation.patch`，不改变原生协议。其 Twister 原始报告在同目录。

## 通信与模拟时延

| 指标 | 原生 PE | RFC N 实验 | 解释 |
|---|---:|---:|---|
| Central 请求 L4 至达到 L4 | 4701 ms | 1001 ms | 各一次 BabbleSim 模拟时钟观测；不代表实板 CPU 或真实空口时延 |
| 成功配对的认证阶段 SMP PDU | 82 条，1394 字节 | 6 条，198 字节 | 按协议消息长度计算；固定 N 分支日志观测到每端 3 条、99 字节 |
| 连同 Pairing Req/Rsp、公钥交换 | 86 条，1538 字节 | 10 条，342 字节 | 理想成功路径的协议层字节，不含 L2CAP、链路层、重传、Keypress 或 GATT |

原生 PE 认证阶段含 20 轮、每轮双方各一条 Confirm 和 Random，共 `20 × 4 × 17` 字节，加两条 17 字节 DHKey Check。固定 N 实验以两条 65 字节掩蔽点、两条 17 字节 Random 和两条 17 字节 DHKey Check 替换这些消息。原生与增强测试程序的其他工作不同，因此上表只比较相同定义的 L4 配对区间；还需重复测量和实板时序才能评估实际延迟与抖动。

Windows `nrf52833dk/nrf52833` 的 `peripheral_hr` 示例编译通过，输出 FLASH 200248 B、RAM 29260 B。这个示例没有运行配对，且当前构建配置只有 512 B 密码堆和 1400 B long workqueue 栈；BabbleSim 配对测试分别配置 32768 B 和 8192 B。因此这些编译体积不是可配对固件的最终资源数据，也不能作为实板成功证据。

## 固定 N 的计算优化判断

N 已以大端 `X || Y` 常量存入固件，运行时不执行压缩点解码或 HashToCurve，也不在空口传输 N。本次 review 去掉了已核验常量 N 在 `read_point()` 中的一次重复曲线校验；非零口令下 `mbedtls_ecp_mul()` 仍验证 N，来自网络的点仍执行原校验。向量和双端仿真通过，BabbleSim 模拟时钟的 1001 ms 没有变化；尚无可据此报告的 CPU 加速百分比。

[Mbed TLS 的固定基点说明](https://github.com/Mbed-TLS/mbedtls-docs/blob/main/kb/how-to/how-do-i-tune-elliptic-curves-resource-usage.md)给出了预计算表换取速度、消耗内存的案例。当前 TF-PSA-Crypto 的 `ecp_mul_comb()` 只识别 `grp.G` 并复用其表；N 虽固定，却不会自动走 G 的表。nRF52833 [没有 CryptoCell 310](https://docs.nordicsemi.com/r/bundle/nwp_057/page/wp/nwp_057/prod_sec_features/dev_features_52.html)，nRF52840 才有该硬件；当前代码还直接调用 Mbed TLS 点接口，不能把硬件功能存在当成已经启用。给 N 增加常驻预计算表可能缩短重复配对的乘法，但会增加 Flash/RAM、改变私有后端依赖，并需要验证恒定时间访存。应先在目标板测量每步曲线运算时间、堆峰值和配对时延，再做隔离的表大小对照实验。

## 合并前仍需解决的可靠性问题

1. 这是动态 `M=abG`、固定 RFC N、自定义口令编码及 SHA-256→BLE `f5`/`f6` 的组合，不等同于 RFC 9382 的标准实例；RFC 的安全证明不能直接套用。需要冻结协议 v1、身份和角色绑定、主动攻击及跨会话模型，并对组合给出可审查的论证。
2. 本分支只支持两端 KeyboardOnly、单连接、SC、指定 TF-PSA 后端。其他配对方式被拒绝，普通 Zephyr 应用的默认栈和堆配置也未验证可运行；合并时必须明确这是作品专用 fork 的支持范围。
3. 所依赖的 Mbed TLS `mbedtls_ecp_muladd()` 在本地 TF-PSA 源码中标为非恒定时间。当前只以公开系数 `+1/-1` 调用，标量乘法另用带 RNG 的 `mbedtls_ecp_mul()`，但对秘密相关点和恶意输入的侧信道行为尚未评估。加入 N 预计算前尤其要解决这一点。
4. 现有负例覆盖错口令、非法点、重复点与失败后重连；尚缺真实恶意对端选点、跨会话重放、并发/断连竞态和资源耗尽注入。固定六位口令还需产品层的在线猜测限制。
5. 固定 N 版本尚无两块真实开发板上的配对日志、真实空口 PCAP、CPU/堆峰值或能耗记录。当前结果不能证明实板端到端可靠。

因此这份记录确认的是**功能回归、旧攻击等式回归和模拟通信收益**。在上述安全与实板门槛得到证据前，不应把本分支称为已验证安全的最终 SPAKE2，也不应以此理由直接快进 `main`。
